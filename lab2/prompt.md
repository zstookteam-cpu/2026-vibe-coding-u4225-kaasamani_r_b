# Промпты для LLM (Лаб. 2 — интеграция с данными)

LLM: Claude. Работа велась диалогом: сначала согласовали выбор интеграции и план, затем сгенерирован код.

## Исходный запрос и согласование плана

**Запрос пользователя:**
> Сделать Лабораторную 2. Подумать, какую интеграцию с API лучше сделать с учётом нашего бота.
> Сделать отчёт по инструкции и загрузить на GitHub. Также хочу, чтобы в Telegram выводились
> доступные команды при вводе «/».

**Ответ LLM (план):** выбран публичный API Open-Meteo (погода) как основная интеграция —
он бесплатный, без ключа и связан с задачами (планирование дня, напоминания); второй источник —
расширение SQLite (`/search`, `/week`). Остальные варианты отклонены: курсы валют не связаны с задачами,
CSV с сотрудниками пришлось бы выдумывать. План: `/city`, `/weather`, погода в `/today` и в напоминаниях,
кэш 10 минут, обработка ошибок, меню команд.

**Решение пользователя:** план утверждён; если город не задан — просить выполнить `/city`
(а не подставлять город по умолчанию).

## Промпт по шаблону курса (исходный)

```
Доработай Telegram-бота-ассистента для задач (Python, python-telegram-bot 21, SQLite, JobQueue).

Текущий функционал бота:
- задачи текстом и командой /add, приоритеты тегами !1/!2/!3, /list, /today, /done, /completed,
  /delete, /priority, напоминания /remind и /unremind (через JobQueue, восстановление после перезапуска),
  данные в SQLite (tasks.db), токен в .env.

Новая интеграция с данными:
1. Публичный API Open-Meteo (без ключа):
   - геокодинг: GET https://geocoding-api.open-meteo.com/v1/search?name=<город>&count=1&language=ru&format=json
     (если город не найден, в ответе нет ключа "results");
   - прогноз: GET https://api.open-meteo.com/v1/forecast с параметрами latitude, longitude,
     current=temperature_2m,apparent_temperature,precipitation,weather_code,wind_speed_10m,
     daily=temperature_2m_max,temperature_2m_min,precipitation_probability_max,
     wind_speed_unit=ms, timezone=auto, forecast_days=1.
2. Команды:
   - /city <город> — найти город через геокодинг и сохранить координаты пользователя в SQLite (таблица users);
   - /weather — погода в городе пользователя (сейчас, ощущается как, ветер, мин./макс. за день,
     вероятность осадков, подсказки: зонт, сильный холод, жара, ветер); /weather <город> — разовый запрос для другого города;
   - /today — добавить строку с погодой; /remind — добавить краткую погоду в текст напоминания;
   - /search <слово> — поиск по задачам пользователя (активным и выполненным), без учёта регистра, в том числе для кириллицы;
   - /week — задачи, созданные и выполненные за последние 7 дней.
3. Если город не задан — просить выполнить /city, город по умолчанию не подставлять.
4. Меню команд: зарегистрировать все команды через set_my_commands с описаниями на русском, чтобы Telegram
   показывал список при вводе "/"; обновить /help и /start.

Требования:
- Простой, читаемый код, комментарии на русском; логика погоды — в отдельном модуле weather.py.
- Обработка ошибок: город не найден, пустой или слишком длинный запрос, таймаут и недоступность API,
  неожиданный формат ответа. Сбой погоды не должен ломать /today и напоминания.
- Таймаут запроса 15 секунд, кэш прогноза на 10 минут.
- Поддержать необязательный PROXY_URL из .env и для запросов к Open-Meteo.
- Не сломать существующий функционал из Лаб. 1.
- Использовать уже установленные библиотеки (httpx входит в python-telegram-bot), новых зависимостей не добавлять.

Создай:
1. Обновлённый bot.py
2. Файл weather.py
3. Обновлённый README.md с командами и инструкцией по запуску
4. Автотесты на подставных ответах API (unittest), чтобы проверить логику без сети
```

## Итерации и улучшения

### Итерация 1 — выбор интеграции
Первый ответ LLM содержал план без кода: сравнение источников данных и предложение Open-Meteo + SQLite.
Пользователь утвердил план и решил, как вести себя боту без заданного города (просить `/city`).

### Итерация 2 — ошибка при самопроверке кода
При разборе кода выявлена проблема: адрес прокси `PROXY_URL` читался при импорте модуля `weather.py`, то есть
**до** загрузки `.env`, поэтому прокси из `.env` не применялся бы к запросам погоды. Исправлено: значение читается
при каждом запросе.

### Итерация 3 — автотесты
Для проверки без сети (API Open-Meteo из среды разработки недоступен) написаны 44 автотеста на подставных ответах:
геокодинг (найден / не найден / сломанный ответ), кэш прогноза, ошибки сети (таймаут, код 500, невалидный JSON),
поиск по кириллице без учёта регистра, спецсимволы `%` и `_`, выборка за неделю, `/today` и напоминания при сбое погоды,
регистрация меню команд, а также что функционал Лаб. 1 не сломан. Все тесты проходят.
